# Contributor Guidelines

Welcome! We're glad you're interested in contributing. This project welcomes contributions from people of all backgrounds, whether you write code, know the I Ching well, or simply found a typo.

## Issues

### Feature Requests

If you have ideas for improving the project, you can suggest features by opening a GitHub issue. Include details about the feature or change, and describe the use cases it would enable.

Feature requests will be tagged as `enhancement` and their status will be updated in the comments of the issue.

### Bugs

When reporting a bug or unexpected behavior, make sure your issue describes the steps to reproduce it, including the browser and operating system you were using and any error messages.

Reproducible bugs will be tagged as `bug` and their status will be updated in the comments of the issue.

### Content Corrections

Much of this project is text about the 64 hexagrams. If a translation, an explanation, or a quoted line is wrong, open an issue that names the hexagram and the line, quotes the current wording, and gives the wording you propose together with the edition or commentary it comes from.

### Wontfix

Issues will be closed and tagged as `wontfix` if we decide that we do not wish to implement them, usually because they are out of scope. We will comment on the issue with the reasoning.

## Contribution Workflow

### Open Issues

If you're ready to contribute, start by looking at the open issues tagged as [`help wanted`](../../issues?q=is%3Aopen+is%3Aissue+label%3A"help+wanted") or [`good first issue`](../../issues?q=is%3Aopen+is%3Aissue+label%3A"good+first+issue").

You can comment on the issue to let others know you're interested in working on it or to ask questions.

### Making Changes

1. Fork the repository.

2. Create a new feature branch.

3. Make your changes. Run `npm test` and `npm run build` locally and make sure that both succeed.

4. Open a pull request with a name and description of what you did. You can read more about working with pull requests on GitHub [here](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/proposing-changes-to-your-work-with-pull-requests/creating-a-pull-request-from-a-fork).

5. A maintainer will review your pull request and may ask you to make changes.

## Code Guidelines

### TypeScript

The code is written in TypeScript with strict type checking. `npm run build` runs the type checker, and `npm test` runs the unit tests. Code, comments, and commit messages are written in English. Commit messages follow the [Conventional Commits](https://www.conventionalcommits.org/) format.

### Content Files

The text for each hexagram lives in JSON files under `src/content/`. The fields of each file are defined in `src/content/types.ts`, and `src/content/content.test.ts` checks every file against the original text.

- `src/content/classics/` is generated by `scripts/fetch-classics.ts`. Do not edit these files by hand. To change a reading, add an entry to `scripts/classics-corrections.json` and run `npm run fetch:classics`.
- `src/content/guide/` holds the beginner notes. A change to an explanation should follow a mainstream commentary and say which one in the pull request.
- `src/content/ni/` holds summaries of Ni Haixia's commentary. Every entry must list the sources it was compiled from, and it must paraphrase the source rather than copy long passages.
